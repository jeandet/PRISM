# PRISM — Review and Plan (2026-11-12)

**HEAD:** `676d19a`.
**Method:** one review by Claude Code. The question: what would someone porting a mid-size Qt
app hit first? Think of an IDE-like tool, a data viewer with docked panels, or a desktop app
with many settings. Every claim was checked with a grep, given below.
**Build:** `meson test`: 111 passed, 0 failed. CI green on all 13 lanes.

---

## 1. Where PRISM stands

The 2026-11-02 plan is done:
- platform services: file dialogs, drag and drop from the OS, message boxes;
- popups that hold widgets, nested popups, dialogs built from real widgets;
- PNG and SVG icons, in buttons, menus and trees;
- graphemes, line breaking, bidi;
- Python bindings for all of that.

The widget catalog is now wide. What is missing is the layer *around* the widgets: what Qt
calls the application shell. Actions, enabled states, shortcuts, windows, panels, settings,
themes. A ported app needs those on day one.

## 2. The gaps, ranked by what a ported app hits first

1. **No disabled state.** No widget can be greyed out. `InteractionState::Disabled` is declared
   (`ui/context.hpp:17`) and never used: `grep -rn Disabled include src` finds only that line.
   Every real app greys out "Save" when nothing changed, or a button while a job runs. Today an
   app has to hide the widget or ignore the click.

2. **No actions or shortcuts.** Qt's `QAction` is one object shared by a menu item, a toolbar
   button and a shortcut, with one enabled state.
   - Menu items are plain strings (`ui/delegate.hpp:260`). There are no separators, submenus,
     check items or shortcut hints (`grep -nE "submenu|separator|checkable"` on the menu
     files: zero hits).
   - The only app-wide key hook is one function, `set_global_key_handler`
     (`app/model_app.hpp:73`). The app must decode Ctrl+S itself, and nothing shows it in the
     menu.

3. **One window, no docking.**
   - An app cannot open a second window. `WindowRegistry` supports several, but
     `model_app` only adds the main window and the debug inspector
     (`app/model_app.hpp:260,399`).
   - No dock panels (`grep -ri dock include src`: zero hits). Splitters exist (`SplitState`,
     `ui/delegate.hpp:168`), so panels can be resized but not moved, tabbed or floated.

4. **Nothing is remembered between runs.** No settings store, no window geometry, no
   splitter sizes (`grep -rnE "Settings|save_state|serialize" include`: nothing relevant).
   This is where reflection pays off: a `Field` struct already knows its members, so saving
   and loading it as JSON or INI is close to free. That fits the "instant UI from a struct"
   pitch: *instant settings from a struct*.

5. **One fixed dark theme.** `Theme` is a struct of colors (`ui/context.hpp:34`). There is no
   light theme, no way to switch at run time (`WidgetTree` has no theme setter), and the OS
   preference is not read (`grep -rn SDL_GetSystemTheme`: zero hits).

6. **Python lags behind C++.** Python can build sliders, checkboxes, radios, spin boxes,
   progress bars, buttons, combo boxes, popups, plots and trees. It cannot build menus,
   dialogs, tabs, tables, text areas or labels. `TableSource` is declared as a protocol
   (`python/prism/__init__.py:117`) and nothing uses it (`grep -c TableSource
   python/src/prism_ext.cpp`: 0).

7. **No drag and drop inside the app.** Files can be dropped from the OS. But nothing can be
   dragged from one widget to another: no tree or list reordering, no tab dragging
   (`grep -rnE "drag_source|start_drag|DragData"`: zero hits). Docking needs this too.

8. **Accessibility export.** Unchanged since the last plan: roles and names exist, nothing
   hands them to the OS, and the access tree has no bounds (`app/access_tree.hpp:23`).

9. **Less urgent for a first port:**
   - translations (no `tr()` or catalog mechanism);
   - printing (SVG export exists, nothing goes to a printer);
   - the scale items carried over: incremental table sort (done, see P3) and undo
     by diffs (`ui/text_edit.hpp:89`).

## 3. Correctness and housekeeping

1. **A popup inside a scrolled area opens off its anchor.** A non-modal popup is placed from
   its anchor's position before scrolling (`app/widget_tree.hpp:1294`, a `simplify:`). Once a
   scroll area holding a popup button is scrolled, the popup opens in the wrong place. Settings
   pages are long and scroll, so a real app will hit this. Fix: add the ancestors' scroll
   offsets. Needs a reproducer test first.
   Fixed 2026-11-12: `anchor_origin` subtracts each ancestor's scroll offset (test in
   `tests/test_popup.cpp`).
2. **A stale note (removed with this review).** `ui/text_metrics.hpp` said Left/Right move in memory order. That was
   fixed on 2026-11-12 (`visual_step`).
3. **`widget_tree.hpp` is 1610 lines again.** (2026-11-13: drag drawing moved to
   `app/drag_draw.hpp` and dock building to `app/dock_builder.hpp`; the tree is 1916 lines
   after a day of features, the popup stack and the drag state machine still inside.) It was split once along the builder / traversal /
   pipeline seam. The popup stack added a new block that could live in its own header.

## 4. Plan

### P0 — the application shell (1–2 weeks)

1. **Enabled state** on every widget: drawn greyed, skipped by focus, ignores input.
   `vb.widget(f).enabled(bool_field)` so it can follow a field.
   Done 2026-11-12: `vb.widget(f).enabled(flag)` and `vb.enabled_if(flag, fn)` (a group, no
   container). The tree is the one gate: no input, focus, hover, press or cursor for a
   disabled widget, and one just disabled drops them. Its drawing is faded (`render::fade`,
   images too); list rows built at run time follow their list's flag. The unused
   `WidgetState`/`Context` were deleted. Left: Python.
2. **Actions:** a value holding a label, an icon, a shortcut and an enabled flag, used by menu
   items and buttons. Menus gain separators, submenus and check items, and show the shortcut.
   The tree routes shortcut keys to the action, whatever has focus.
   Done 2026-11-12, without a separate action type: menus are the actions. A `ui::MenuItem`
   has a text, a `Shortcut`, an icon, an enabled flag, a check mark, or is a separator. A
   shortcut chooses its item from anywhere (`WidgetTree::trigger_shortcut`), except keys a
   focused text widget keeps (Ctrl+C copies there); not while a popup is open.
   `ui::on_choice` reports user choices only. The notes app uses all of it (Ctrl+S, Save
   greyed while unmodified). Left: submenus; a button showing a shortcut.
3. **Settings from a struct:** save and load a `Field` struct through reflection (with a
   manual fallback without `-freflection`, as for views). Window size and splitter sizes come
   along for free.
   Done 2026-11-12 with Glaze (TOML) instead: its own reflection works in every build, so no
   manual fallback is needed. `app::SettingsFile` loads a struct of fields and saves it after
   each change (a short pause gathers a burst, written on its own thread, through a temporary
   file and a rename); `backends::settings_dir` is SDL_GetPrefPath. The notes app reopens the
   last file. Window size and splitter sizes followed the same night:
   `app::WindowGeometry` + `AppContext::remember_window_size`, and `vb.remember_split` with a
   `Field<ui::SplitSizes>` (read when built, written when a drag ends; sizes for another
   number of panes are ignored). The notes app reopens at its size and split. Left: in the
   browser the file is not kept (needs IDBFS); keys a newer version wrote are dropped on the
   next save; window position and maximized state.
4. **Themes:** a light theme, a setter that repaints, and following the OS preference.
   Done 2026-11-12: `ui::light_theme()` (WCAG AA contrast, tested), `WidgetTree::set_theme`,
   `AppContext::set_theme` / `follow_system_theme` (a `SystemTheme` event from the backend, at
   start and on `SDL_EVENT_SYSTEM_THEME_CHANGED`). The snapshot carries the window's own colors
   (`SceneSnapshot::window`), so the background and title bar follow too. One-color icons are
   `render::symbolic` and take their text's color (`ImageCmd::tint`). The gallery's Theme
   dropdown applies and remembers it.

### P1 — windows and panels (weeks)

5. **Several app windows,** each with its own model view.
   Done 2026-11-12: `AppContext::open_window(model, config)` (through the backend's existing
   `request_window`, as the debug inspector does), `window_open`, `close_window`; a new window
   takes the app's theme. model_app now also publishes right after `setup`, so what setup
   changes (a theme, a window) shows without waiting for an event. The notes app opens a live
   statistics window (View > Statistics window, Ctrl+I). Left: the browser has one canvas.
6. **Drag and drop inside the app:** a drag source, a drop target, and a preview.
   Design proposal written 2026-11-12, for review: `doc/design/drag-and-docking.md` (also
   covers item 7). Done 2026-11-13: typed drags, reorderable lists, tree moves, Python.
7. **Docking panels:** tabbed, split, floating; their layout saved by item 3. Needs 5 and 6.
   Rebuild the System Monitor on it, to find what breaks.
   Done 2026-11-13: layout value, moving panels (they keep their widgets), floating panels,
   Python; the System Monitor is a dock. Left: dragging between windows.

### P2 — reach

8. **Python parity:** menus, dialogs, tabs, tables, text areas, labels, and the P0 shell.
   Part 1 done 2026-11-12: `vb.widget(h, enabled=flag)`, `vb.enabled_if(flag, fn)`,
   `prism.menu` / `prism.context_menu` with shortcuts, separators, check items and
   `.on_choice(cb)`; `ui::parse_shortcut("Ctrl+S")` in C++; `prism.set_theme`.
   Part 2 done 2026-11-13: drag and drop, reorderable lists, docking, labels, text areas, tabs,
   dialogs, tables over a Python object, `prism.open_window`, `prism.settings_dir`. Python
   saves settings with its own json/tomllib. Python is now level with C++ for an app's
   widgets and shell.
9. **Accessibility bridge** (AccessKit, decided 2026-11-02).

### P3 — when a task touches the area

10. Translations, printing, incremental table sort, undo by diffs, incremental layout
    (measured 2026-11-02: not needed below ~10k live widgets).
    Incremental table sort done 2026-11-13: a sorted table over a `List` re-sorts only the
    rows updated or appended, and merges them back. 100k rows: 1 ms instead of 32 ms
    (`benchmarks/table_sort.cpp`). Removals and column-storage tables still re-sort all.

## 5. Checked and ruled out (don't re-flag)

- **"No splitter."** There is one: `SplitState` (`ui/delegate.hpp:168`) and `SplitDrag`
  (`app/widget_tree.hpp:429`).
- **"No spin box."** `SpinBox<T>` (`delegates/form_delegates.hpp:216`), also in Python.
- **"No high-DPI."** The SDL window reads the pixel density (`src/backends/sdl_window.cpp:251`),
  and the pixel tests render at 1x and 2x.
- **"No timers or animation."** `app/deadline_timer.hpp`, `ui/animation.hpp`.
- The 2026-11-02 list (plot interaction) still holds.
