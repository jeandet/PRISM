## 1. Where PRISM stands

The 2026-11-01 plan is done through P2:
- P0 and P1: text, clipboard, input methods, measurement, the glyph cache.
- P2: accessibility metadata, images, menus, context menus, dialogs, tooltips, table
  interaction, small widgets.
- P3 #17: input is hit-tested against the frame on screen.

A second renderer (WebGPU) draws real apps on desktop.

What is left is not the core. Both reviews agree the next gap is **the app can't talk to the
platform**. Grep for `SDL_ShowOpenFileDialog`, `SDL_EVENT_DROP`, `SDL_ShowMessageBox` or
`SDL_GetDisplays`: zero hits. `BackendBase` (`include/prism/app/backend.hpp:29-46`) has no
hook for them. Today `model_notes` is a file editor that can't show an Open dialog.

## 2. The gaps, ranked by what a real app hits first

1. **Platform services.** No file dialogs, no drag and drop, no message box, no
   multi-monitor information. SDL3 provides all of them, including a portal-backed file
   dialog on Linux. The seam already exists: the backend hands the tree a `TextMeasurer`
   and a `Clipboard`, and these would be more of the same.
2. **Popups that hold widgets.** A dialog paints its own title, message and buttons
   (`delegates/dialog_delegates.hpp`, see its `simplify:`). So there's no preferences dialog
   with real fields, and no popover attached to a widget. opencode argued for this when the
   long-message fix went in.
3. **Widget depth.**
   - The dropdown is choose-only; there's no editable combo box (no `TextInput` in
     `dropdown_delegates.hpp`).
   - Table cells are text only (`paint_table_row`, `widget_tree.hpp:1235`).
   - Progress has no "busy" mode (`form_delegates.hpp`, `simplify:`).
4. **Icons.** Images are raw RGBA only (`render/draw_list.hpp`, `simplify:`), so toolbars,
   trees and logos can't use PNG or SVG.
5. **Text beyond Latin.**
   - Positions step by code point, not grapheme (`core/utf8.hpp`), so an emoji or a
     combining accent splits.
   - Lines break only at spaces (`ui/text_metrics.hpp`).
   - There's no bidi, so Arabic and Hebrew put the caret on the wrong side.
   - HarfBuzz arrives through SDL_ttf, so this means exposing what it knows, not writing a
     shaper.
6. **The accessibility bridge.** Roles, names and values exist. Nothing exports them, and
   the access tree has no bounds yet (`app/access_tree.hpp`, `simplify:`).
7. **Scale.**
   - Layout runs on the whole tree every publish, and nobody has measured 10k ordinary
     widgets.
   - A table re-sorts on every data change (`ui/table_ops.hpp`).
   - Undo copies the whole text per edit (`ui/text_edit.hpp`).
8. **Windows.** No CI lane, and the installed-font lookup is Linux/macOS only
   (`src/backends/font_lookup.cpp`).

## 3. Plan

### P0 — platform services (days)

**Status:** #1 done on 2026-11-02 (`app/platform_services.hpp`, `AppContext::choose_files` and
`show_message`, SDL through `QueuedPlatformServices`; File > Open… and Save As… in `model_notes`).
#2 done on 2026-11-02: `FileDrop`/`TextDrop` input events (one event per drop), dropped text
typed into the text widget under it, `AppContext::on_file_drop`; dropping a file on
`model_notes` opens it. #3 (message box) went in with #1 (`AppContext::show_message`).

1. **File dialogs.** Add a `PlatformServices` hook on the backend, like `Clipboard`. Open,
   save and choose-folder use `SDL_ShowOpenFileDialog` and friends. They are asynchronous:
   the answer is posted to the logic thread. Dogfood it in `model_notes` as File > Open… and
   Save As….
2. **Drag and drop.** Map `SDL_EVENT_DROP_FILE` and `SDL_EVENT_DROP_TEXT` to an input event
   routed to the widget under the pointer. Example: a file dropped on the notes editor opens.
3. **Message box** for errors the app can't show in its own window. Use
   `SDL_ShowMessageBox`.
4. **A Windows CI lane** (decision 2 in §4), added with the services so they get a Windows
   path from the start.

### Not planned now

- **A third renderer, or a runtime backend loader.** Finish WebGPU parity first. Nothing
  needs runtime selection.
- **More wait-free work.** It was measured: no stall.
- **A stylesheet engine or declarative language.** Fields and reflection are the wedge;
  extend `Theme` tokens instead.
- **Our own shaping or bidi.** Use HarfBuzz through SDL_ttf, and a library for the Unicode
  algorithms.
- **Docking panels.** They come after file dialogs and popups with widgets, since they
  need layout persistence, drag targets and hosted subtrees.

## 4. Decisions (made 2026-11-02)

1. **Dependencies: one interface per service, like Qt's platform plugins.** Each service is a
   small interface with one implementation picked at build time (a meson option):
   `PlatformServices`, `ImageDecoder`, `TextSegmenter` and `AccessibilityBridge`. Changing an
   implementation later touches one file. Loading it at runtime, as QPA does, stays possible
   because the interface is the only seam. It is not needed yet.

   | Service | Implementation | Why |
   |---|---|---|
   | Platform services (P0) | SDL3 | Already the platform layer |
   | Images (P2 #9) | SDL3_image | Same family and zlib license as SDL3/SDL_ttf; on WrapDB; Emscripten port; PNG and SVG built in |
   | Graphemes, line breaks (P2 #10) | libunibreak | Small, zlib license, on WrapDB, fine for wasm. ICU (~30 MB of data) is too heavy for the web build |
   | Bidi (P2 #10) | SheenBidi | Apache-2.0, so static wheels carry no LGPL obligations (fribidi's catch). Not on WrapDB: our own build file, one unity C source |
   | Accessibility | AccessKit C bindings | Prebuilt per platform, packaged like wgpu-native |

2. **Windows: yes, a CI lane.** It goes in with P0, so the new platform services get a
   Windows path from the start. Expect C++26 compiler work: MSVC's support may not be
   enough, and MSYS2's GCC or clang are the fallback.
3. **The browser build with WebGPU: later.** The question was whether to spend a session on
   it. Testing it needs a browser that can use the GPU, and headless Chromium in this
   container could not (flags tried 2026-11-02). It stays on the roadmap and waits for a
   machine with a GPU browser.
